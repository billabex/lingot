# Colors

## Global vs Semantic — two layers, one system

The color system is organized in **two layers**:

<table>
  <thead>
    <tr>
      <th>Layer</th>
      <th>Purpose</th>
      <th>Import</th>
      <th>When to use</th>
    </tr>
  </thead>
  <tbody>
    <tr>
      <td><strong>Global</strong> (primitive)</td>
      <td>The raw palette — every color value the design system knows.</td>
      <td><code>colors</code></td>
      <td>Almost never directly. These are the building blocks.</td>
    </tr>
    <tr>
      <td><strong>Semantic</strong></td>
      <td>Purpose-based aliases that reference globals.</td>
      <td><code>bg</code>, <code>text</code>, <code>action</code>, <code>status</code>, <code>border</code></td>
      <td>Always. Components and app code should use these.</td>
    </tr>
  </tbody>
</table>

**Why two layers?** Semantic tokens decouple _intent_ from _value_. `bg.default` means "default background" — today it's white, but it could change to cream tomorrow. If you used `colors.solid.white` directly, you'd have to update every callsite. With `bg.default`, you update one line in `semantic.ts` and everything follows.

```
Global (palette)         Semantic (intent)
─────────────────        ─────────────────
colors.solid.white   ←── bg.default
colors.neutral[700]  ←── bg.inverse
colors.neutral[700]  ←── text.primary
colors.neutral[700]  ←── action.primary
colors.red[600]      ←── status.error
colors.red[600]      ←── action.destructive
colors.red[600]      ←── border.error
```

Notice how the same global value (`neutral[700]`) can serve multiple semantic purposes, and a single palette change propagates everywhere automatically.

## Usage

```ts
import { bg, text, colors } from "@billabex/ui-tokens";

// Semantic tokens (recommended)
bg.default.hex          // '#ffffff'
bg.default.rgba(0.5)    // 'rgba(255, 255, 255, 0.5)'
text.primary.hex        // '#1c1917'

// Global tokens (only when needed)
colors.neutral[700].hex // '#1c1917'
colors.gold[500].hex    // '#d4a853'
```
